## Task 6 evidence and implementation decisions

The user approved all six tasks and sequential implementation with independent review. The Task 6 implementer reported the following concrete defects and smallest proposed fixes to the controller before expanding source scope. The controller then became unavailable with a model-capacity error. Work continued within the approved acceptance requirements. After resuming, the controller reviewed the concrete evidence and adopted the narrow scope in four further rulings preserved above. Independent review remains required; the following implementation details do not waive that gate.

1. **Reject changed stagnation configuration at the controller boundary.** Actual compiled CLI acceptance resumed a completed task with a changed threshold and returned 0. The earlier Task 5 integration test explicitly expected the changed input to be ignored. Task 6 expressly requires conflicting threshold refusal. The controller now compares the parsed task threshold against the validated saved threshold before resuming. An initial store-level check broke the store's separately established contract of retaining saved option values; that change was removed, and the existing store test remains unchanged. Evidence: `tests/cli/loopLifecycle.test.mjs` conflict cases and `tests/integrations/loopController.test.ts` “rejects changed thresholds on a complete continue checkpoint without resetting it”. Cost if wrong: a user who edits the task configuration must restore it or create a reviewed task; no ledger migration, new authority or count reset is introduced.

2. **Await genuine background outcome persistence.** The actual compiled `--bg task` worker called the local provider and completed its real service turn, then exited 1 with “Persistence lock is busy” when the synchronous outcome writer collided with the supervisor's asynchronous metadata writer. A new asynchronous counterpart uses the existing bounded leased writer; `runSingleTask` awaits it. The synchronous API and its contract remain available. Evidence: real worker log captured in `task-6-background-diagnostic.log` during implementation, and the genuine background acceptance case in `tests/cli/loopLifecycle.test.mjs`. Cost if wrong: successful task exit can wait for the existing bounded metadata lease; persistence failure still surfaces and cannot be reported as accepted completion.

3. **Recognize a received ready signal even if the verified worker exits before the supervisor polls again.** A separate real worker run had outcome `completed`, exit 0 and released its session, but the launcher failed with “Worker exited before ready (exit 0)”. Readiness now recognizes the actual previously received `ovogo:ready` event after process identity verification; normal physical tree cleanup and terminal outcome checks still run. Evidence: the same genuine background acceptance, plus existing `tests/backgroundProcessLifecycle.test.ts`. Cost if wrong: launcher success can coincide with a task that already finished; launch readiness still does not establish task success, which requires the durable outcome.

4. **Select the newest Loop session before checking its ledger.** A real second CLI process was killed after durable prepared publication but before history existed. `--continue` incorrectly skipped that newest session and returned the older completed task with exit 0. Loop-specific latest selection now includes that newest session, then lets the existing controller refuse incomplete recovery. Ordinary session selection keeps its existing behavior. Evidence: `tests/cli/loopLifecycle.test.mjs` “selects the latest incomplete session for --continue without falling back to older completion”. Cost if wrong: a newer empty or damaged session blocks Loop continue and requires an explicit reviewed selection; it never silently resumes older work.

5. **Place clean-checkpoint interruption after workspace ownership release.** The first fixture parked at store checkpoint return while the enclosing workspace guard still owned its lease. Killing there correctly required explicit workspace recovery. The complete-checkpoint test now parks on entry to the next context build, before prepare and after the previous guard released. Prepared, real append-before-receipt and settled-before-checkpoint barriers remain at their exact synchronous boundaries. Evidence: `tests/fixtures/loopControllerChild.mjs`, compiled CLI recovery cases, actual second HTTP payload, ledger phases and counts, non-idempotent append count, and persistent request-budget assertions. Cost if wrong: this batch promises recovery only between complete, released checkpoints; it does not claim automatic recovery from arbitrary instruction boundaries or unresolved resource ownership.

6. **Keep ordinary REPL cancellation out of error-feedback continuation.** The full suite reproduced a Task 1 integration regression: a genuine service cancellation has status `cancelled` with reason `error`; the REPL treated that as an error-feedback request, consumed EOF and then asked again. The existing raw SIGINT test failed with exhausted input. The adapter now excludes cancelled results from that branch. Evidence: `tests/cli/replLifecycle.test.ts` “routes raw readline SIGINT to cancellation and releases the listener” additionally asserts exactly two input reads and no interruption-feedback prompt. Cost if wrong: cancellation returns to the ordinary prompt while explicit interrupted/error/limit continuation keeps its existing behavior; no service outcome or reason is rewritten.

7. **Maintain existing isolated test harnesses when dependencies and typed facts change.** The first full suite showed `budgetTimezone.test.ts` omitted Task 1's new `outcome.js` dependency from its temporary transpilation; `hooksRuntimeIntegration.test.ts` still expected generic blocked instead of the actual structured failed `permission_denied`/hook result. The fixture now includes the actual dependency and the assertion checks the precise denial while retaining the no-write assertion. The setup-script fixture now explicitly binds its own pinned mock pnpm path instead of inheriting npx's package-manager context. Evidence: first full suite 5346 passed/8 failed/14 skipped, followed by the exact six-file serial diagnosis and a 108-test passing regression gate. Cost if wrong: tests depend on actual runtime imports and explicit fixture environment; no production dependency, hook semantics or package-manager behavior changes.

8. **Wait for verified supervisor death before removing its Windows working directory.** The existing background environment fixture repeatedly failed cleanup with EPERM after stopSession had confirmed worker termination but before the supervisor exited its cwd. Cleanup now inspects the recorded supervisor identity until dead/mismatched and never treats unknown as terminated. Evidence: the original full and serial diagnostic runs both reproduced this cleanup failure; the corrected six-file/108-test gate passed. The artifact-policy cleanup EPERM from the first full run passed unchanged in both serial diagnosis and regression gate; no artificial time budget or source timeout change was applied. Cost if wrong: fixture cleanup waits within the existing bounded identity check, and failure remains visible rather than deleting a live process's working directory.
